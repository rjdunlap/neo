# Claude for 3D models and animation, 2026-11-22

*Research review: findings and recommendations only. Nothing here changes the app or the roadmap; the verdicts are judgements from the cited sources, not tested recipes. Researched from public web sources on 2026-11-22 against `origin/main` at `d2596957e`.*

The question: what are the current tools, workflows and practices for making good-looking 3D models and animation with Claude, and which of them are worth adopting for this project's illustrated creatures?

## Summary: Claude builds 3D best as code

As of November 2026, the 3D work Claude does well is the 3D it can write as code and then look at: Three.js geometry in TypeScript, parametric Blender Python run headless, and deterministic glTF scripts, each closed by a render that Claude reads back and a human who approves the look. The best-documented successes are browser games whose models and animation are code, not meshes authored in a modeling tool, and their own author calls the unsupervised results impressive but mediocre as finished art ([Willison, 2026-08-05](https://simonwillison.net/2026/Aug/5/raccoon-heist/)). Live Blender MCP sessions, hosted 3D generators and auto-riggers all work, but each breaks one of the things a small repo-owned art pipeline depends on: reproducibility, a consistent style across many assets, or clips for non-humanoid creatures. Organic characters, deformation-ready topology, improvised rigging and "does it look right" remain weak points in every source, although most of that evidence is vendor commentary or single-user anecdote and none of it tests the newest Claude models on soft, toy-like characters. For Puddle Island the conclusion is conservative: the current pipeline (image-model illustration, code-driven mesh rig, preparation steps in the repo) is already the form of character art an assistant authors most reliably, and nothing found beats it for soft illustrated creatures on a phone. Three things are worth adopting now, none of which adds a 3D runtime: a deterministic contact-sheet review harness, a separate reviewer that sees only renders and a written style bible, and an offline bake script for the specific cases where a creature needs many angles, poses or wearable variants. Real-time 3D in the shipped app should wait; the first-party `@pixi/3d` add-on is ten days old at v0.1.0 and needs a newer PixiJS than the repo has, and iOS memory limits make a second renderer the riskiest option.

## Two Blender routes exist, and only the headless one is reproducible

There are now two free MCP servers for Blender. The **official Blender Lab server** became Claude's verified "Blender" connector in April 2026, described by Anthropic as a natural-language interface to Blender's Python API for analysing scenes, batch scripting and adding tools to Blender's interface ([Anthropic](https://www.anthropic.com/news/claude-for-creative-work); [connector listing](https://claude.com/connectors/blender)). A competitor's comparison, the most detailed source available because the project's own pages could not be fetched, reports **v1.0.3, GPL, Blender 5.1 or later, 26 tools, no asset generation or asset libraries**, and that it runs model-written Python with no guards, with a virtual machine recommended ([StraySpark](https://www.strayspark.studio/blog/official-blender-mcp-server-comparison-2026)). One press summary gives Blender 4.2 as the minimum instead; the version requirement is unconfirmed from a primary source. The community server, renamed **MCP for Blender** in September 2026, works from Blender 3.0, adds a multi-angle `look` tool for visual checks, asset search across Poly Haven and Sketchfab, and a `generate_3d` tool wired to Meshy, Tripo, Rodin and Hunyuan3D. Its README is frank about the cost: arbitrary Python execution, a socket with "no authentication or encryption", safe mode that is opt-in through `BLENDER_MCP_SAFE_MODE=1`, and anonymous telemetry on by default unless `DISABLE_TELEMETRY=true` ([README](https://raw.githubusercontent.com/ahujasid/mcp-for-blender/HEAD/README.md)). It collected at least three CVEs in 2026, including a path traversal giving persistent code execution ([NVD CVE-2026-66004](https://nvd.nist.gov/vuln/detail/cve-2026-66004)). The paid StraySpark alternative is untested on macOS by its own account.

A live session is good for exploration and poor as a source of truth. Each MCP execution starts with a fresh Python namespace, so objects must be found again by stable names ([cc-blender-skill](https://cdn.jsdelivr.net/gh/roble3/cc-blender-skill@main/README.md)); one film project found the agent sometimes "adds a second camera instead of moving the first one" and called the render-inspect loop "slow and expensive" ([Rex Marks The Spot](https://rex-marks-the-spot.pages.dev/blog/posts/blender-llm-integration-research.html)); and a published test reported that a Blender crash left the connection down until both programs restarted ([WindowsForum summary of MakeUseOf](https://windowsforum.com/news/blendermcp-lets-claude-code-run-arbitrary-python-in-blender-projects.445776/)).

The alternative is to have Claude Code write `bpy` scripts and run them with `blender --background --python`. Three small 2026 repositories converge on the same design, which matters more than any one of them since each is a single practitioner's work with almost no adoption. **blendpipe** defines models as Python modules, builds meshes from fixed vertex lists with seeded randomness, runs Blender with `--python-exit-code 1` because Blender otherwise exits 0 when a script fails, and has a test that builds twice and compares bytes; it also renders review sheets (each model against a ruler, from the back, a filmstrip per animation clip) even when checks fail, on the stated lesson that validators cannot catch a floating hat ([blendpipe](https://github.com/sanvisser/blendpipe)). **blender-sprite-pipeline** is the closest published analogue to this project: headless Blender renders flat data passes through orthographic cameras, numpy and Pillow shade them into 2D sprites, the Blender version is recorded in metadata, `--factory-startup` removes state, and the repo ships agent rules requiring a self-test first and a look at rendered output after every change ([blender-sprite-pipeline](https://github.com/denis30volovic/blender-sprite-pipeline)). A third pipeline adds the order of work that recurs everywhere: reference, blockout, silhouette review, detail, neutral and game-camera previews, validation, then a GLB export that is re-imported and verified before it replaces the old file ([blender-lowpoly-assets](https://github.com/0x0bug/blender-lowpoly-assets)). No source measured headless against MCP head to head. The reasonable reading is to explore through MCP if at all, then have Claude write the result out as a standalone build script and treat only the script as real.

Quality advice from users is consistent. Give exact measurements, because Claude otherwise guesses dimensions. Learn the domain vocabulary and ask for parametric controls: one user of the official server with Opus found a generic table generator mediocre until Claude was told to research furniture terminology and expose units and defaults, and summed the model up as a fast inexperienced intern, "not a magic genie" ([Hacker News](https://news.ycombinator.com/item?id=50443618)). Map mood words to concrete light and camera settings, since "more dramatic" does not translate. Animation splits the same way. Improvised bone placement and weight painting on an arbitrary mesh is described as unreliable ([MindStudio](https://www.mindstudio.ai/blog/claude-blender-mcp-real-world-performance)), yet blendpipe exports skinned, animated GLB by fixing the rig in code, defining clips as pose functions over normalised time, and validating skin weights and foot sinking numerically. Animation succeeds where rig and motion are deterministic code with checks, and fails where the model must judge by eye. Anthropic publishes no Blender skill; community packs exist (an 8-skill plugin for Blender 5.0/5.1, a roughly 30-skill pack whose own README says Claude Code routing is still awaiting community testing), and a short project-local skill that pins the Blender version, the build flags, the palette and the review-sheet step is likely worth more than either ([ra100 plugin](https://github.com/ra100/blender-claude-plugin); [cc-blender-skill](https://cdn.jsdelivr.net/gh/roble3/cc-blender-skill@main/README.md)).

## Generators deliver a first-pass mesh; creature animation is still handmade

The hosted leaders are **Meshy 7.1**, **Tripo** (H3.1 for detail, P1 and P2 for native low-poly), **Hyper3D Rodin Gen-2.5** and **Tencent Hunyuan3D 3.1**; the open-weight leaders are TRELLIS.2, Hunyuan3D 2.1 and the newly opened Hi3D ([inker.si](https://inker.si/blog/best-ai-3d-model-generators-2026); [Cinevva guide](https://app.cinevva.com/guides/ai-3d-model-generators)). Meshy and Tripo are positioned for stylized game assets, Rodin and Hunyuan for realism, but that positioning comes from vendor and reseller pages; no independent 2026 comparison on cartoon characters with a stated method was found. All of them are strongest as image-to-3D, which has a practical consequence: style consistency across a cast comes from the 2D concept stage, not from the 3D generator.

From Claude Code, **Meshy has the only official headless integration covering the whole chain**: an MIT-licensed MCP server with 28 tools spanning generation, remesh, rig, animate, text-to-motion and download, plus a skill pack that calls the REST API directly ([meshy-mcp-server](https://github.com/meshy-dev/meshy-mcp-server); [Meshy docs](https://docs.meshy.ai/api/ai)). An API key requires a paid plan, listed at $20 a month for Pro, and credit prices put one textured, remeshed, rigged character with a few clips at roughly 45 to 55 credits ([Meshy API pricing](https://docs.meshy.ai/api/pricing.md); [meshy.ai/pricing](https://meshy.ai/pricing)). Tripo's official MCP is alpha and requires Blender, but its REST API is scriptable and exposes dated rig model versions ([tripo-mcp](https://github.com/VAST-AI-Research/tripo-mcp); [Tripo docs](https://developers.tripo3d.ai/en/docs/animations-rig)). Churn is fast: Tencent retired its older hosted endpoints on 2026-10-20. Reproducibility with a hosted generator therefore means pinning the model ID, committing the input images, parameters and the generated file as source art, and making everything after generation a deterministic script. No source evaluated seed control or run-to-run determinism.

The output is a starting mesh. Default face counts run from 150,000 to 500,000 against a game-character budget Tripo itself puts at roughly 5,000 to 30,000 triangles ([inker.si](https://inker.si/blog/best-ai-3d-model-generators-2026); [Tripo blog](https://www.tripo3d.ai/blog/ai-character-models-for-games)). Raw meshes come with messy topology, blurry faces and scattered UVs, single-view inputs invite invented geometry on the hidden side, and automatic remeshing is "generally not final topology for deforming characters" ([Creatune](https://www.creatuneagency.com/en/blog/ai-concept-to-game-ready-3d-character/); [wavect](https://wavect.io/blog/ai-3d-model-generators-game-development-2026/)). Cleanup (merge, recentre, decimate, smooth, downsize textures) is exactly the kind of work a headless Blender script does well.

Rigging and animation are where creature games run out of road. The one independent hands-on test used a single humanoid: Tripo gave the cleanest retarget but over-smoothed shoulder weights, and Meshy placed hip pivots 5 to 15 cm off, causing foot sliding ([StraySpark rigging test](https://www.strayspark.studio/blog/ai-auto-rigging-showdown-2026-tripo-meshy-cascadeur-mixamo)). For non-humanoids, Tripo's v2.5 rigger accepts quadruped, hexapod, octopod, avian, serpentine and aquatic types, but Meshy's API rigs humanoids only, and animation libraries are thin: a competitor's survey reports 90-plus clips for Tripo bipeds against **one walk cycle per creature type and none for birds** ([Tripo docs](https://developers.tripo3d.ai/en/docs/animations-rig); [afk.ai](https://afk.ai/best-auto-riggers-for-animals)). Open text-to-motion models assume one fixed humanoid skeleton ([QtMeshEditor issue](https://github.com/fernandotonon/QtMeshEditor/issues/1073)), and the open auto-rigger UniRig gives every mesh its own skeleton, so clips do not transfer between models. A cast of cute non-humanoid creatures would get rigs from these services and still need its idle, hop, eat and celebrate clips authored by hand or in code, on a shared skeleton per body plan, which is what the project's mesh rigs already do in 2D.

Licensing and local running narrow the choice further. Paid Meshy and Tripo tiers grant private, commercial-use output; Meshy's free tier is CC BY 4.0 and Tripo's is public and noncommercial ([Meshy docs](https://docs.meshy.ai/en/webapp/pricing); [Cinevva guide](https://app.cinevva.com/guides/ai-3d-model-generators)). TRELLIS.2 is MIT but pulls in a gated image encoder and a non-commercial background remover ([model card](https://huggingface.co/microsoft/trellis.2-4b); [trellis2-mlx](https://huggingface.co/xocialize/trellis2-mlx)); Tencent's community licences exclude the EU, UK and South Korea ([Hunyuan3D-2 LICENSE](https://huggingface.co/tencent/Hunyuan3D-2/blob/main/LICENSE)). The vendors' terms were not read directly, so whether assets stay licensed after a subscription ends is unconfirmed. On Apple silicon, a hands-on test of the community TRELLIS.2 port on an M1 Max needed about 18 GB at peak and 5 to 11 minutes for untextured geometry; texture baking took 66 to 224 minutes and produced unusable results, and **a chibi-style input produced a broken, lumpy mesh** ([lilting.ch](https://lilting.ch/en/articles/trellis2-m1-max-hands-on)). Local generation on a Mac yields untextured shape at best, and open auto-riggers need NVIDIA hardware.

## Code-first Three.js is Claude's strongest 3D, and PixiJS now has three ways in

Simon Willison's October 2026 posts are the best independent evidence. He built four Three.js games, none needing more than about four hours of his own time plus long unattended agent runs, and wrote that Claude "doesn't have its own image generation model" but builds "full-color 3D models that look and feel excellent" ([Willison, 2026-10-28](https://simonwillison.net/2026/oct/28/vibe-game-development)). In Battle Drones, Claude wrote 9 buildings, 16 vehicles and 3 infantry units as TypeScript, with no modeling tool, and built its own model-browser page to inspect them ([Willison, 2026-10-20](https://simonwillison.net/2026/Oct/20/battledrones/)). The limits are as clear. Animation in these games is coded motion (legs on a sine, a body bob tied to speed), the style is whatever the model picks, and where textures or key art mattered he still called an image model from a committed script, the same split this project uses. Complex games needed many rounds of human playtesting, and one build consumed nearly two days of agent time and "millions of tokens". No source shows code-built 3D producing soft illustrated characters comparable to image-model sprites.

The main technical failure is version drift. Claude's training data mixes many Three.js releases, so it writes code for the wrong one; a community skill pack exists for that stated reason and lists the renames models still miss, among them `RGBELoader` to `HDRLoader`, `Clock` to `Timer` and `PostProcessing` to `RenderPipeline` ([threejs-skills](https://github.com/cloudai-x/threejs-skills)). Three.js is at **r187** and publishes its own `llms.txt` and full inline docs, whose guidance still says "Use WebGLRenderer (default, mature)" and reserves WebGPU for custom node shaders and compute ([threejs.org/docs/llms.txt](https://threejs.org/docs/llms.txt); [releases](https://github.com/mrdoob/three.js/releases)). Skills go stale within months (the pack above targets r186), so the durable practice is to pin the exact version in `package.json` and load the official LLM docs for that version. For assets, glTF-Transform 4.5 is a scriptable Node library and CLI that inspects, simplifies, resamples and compresses, which lets the whole pipeline live in a repo script ([gltf-transform.dev](https://gltf-transform.dev/cli)); one guide recommends Meshopt over Draco for animated characters because Draco leaves animation tracks and morph targets uncompressed, a claim resting on the format specs, not on benchmarks ([Cinevva optimisation guide](https://app.cinevva.com/guides/optimize-glb-for-web)).

Getting 3D into a PixiJS 8 app has three real routes. PixiJS documents sharing one WebGL context with Three.js: create the Three renderer with a stencil buffer, initialise Pixi on its context with `clearBeforeRender: false`, and call `resetState()` on each renderer every frame; textures are not shared and both renderers must stay the same size ([PixiJS guide](https://pixijs.com/8.x/guides/third-party/mixing-three-and-pixi)). The first-party **`@pixi/3d` v0.1.0** went public on 12 November with glTF loading, named clip playback, lights, shadows and post effects, and requires pixi.js `^8.23.0`; this repo's `package.json` pins `^8.22.0`. Its release page states no licence and lists many breaking changes through the betas ([pixijs/3d releases](https://github.com/pixijs/3d/releases)), and Claude has essentially no training data for it. The third route is to keep 3D out of the app and bake it to sprites offline.

iOS decides between them. WebGPU shipped in Safari 26 but canvas-flicker bugs were still reproduced in 26.2 ([WebKit bug 301627](https://bugs.webkit.org/show_bug.cgi?id=301627)). More seriously, WebGL-heavy pages on iPhone and iPad are terminated under memory pressure and reloaded, sometimes in a loop, and a WebKit comment puts the content-process limit on most iPhones at 1.5 GB ([WebKit bug 300782](https://bugs.webkit.org/show_bug.cgi?id=300782); [WebKit bug 268816](https://bugs.webkit.org/show_bug.cgi?id=268816)). These findings were seen in search summaries, not read in full, and no authoritative current memory figures exist. They still point one way for a phone-first offline PWA: a second renderer and its dependencies are added risk and precache weight for a benefit the game has not yet needed. Editor-centred formats (Spine, Rive, Lottie) do not change this. Spine has an official PixiJS 8 runtime ([Esoteric Software](https://esotericsoftware.com/blog/spine-pixi-v8-runtime-released)), but their value comes from a human animator working in an editor, and no evidence was found of Claude authoring them well.

## The feedback loop and the style bible decide whether output is good

Benchmarks and practitioners agree on what the model gets wrong and on what fixes it. On a mid-2026 code-to-3D benchmark, models recovered overall shape and meaning (a semantic score near 0.8 for the best model) but not geometry (about 0.35), with wrong part counts and weak assemblies; Claude Opus 4.6 sat in the second tier behind GPT-5.5 and Gemini 3.1 Pro ([P3D-Bench](https://arxiv.org/html/2606.11152v2)). No benchmark results were found for Opus 5, Opus 5.5 or Fable 5, and none covers rigging or character animation at all. That gap coexists with Willison's praise without contradiction: stylized low-poly props tolerate exactly the errors benchmarks penalise. The practitioner lists of what fails (organic shapes, animation curves and timing, "anything requiring visual judgment") come mostly from vendor-adjacent blogs that name no model, so they may be partly out of date, but nothing independent has overturned them ([MindStudio](https://www.mindstudio.ai/blog/claude-blender-mcp-real-world-performance)).

What helps is looking, from several views, with a separate judge. The VIGA paper pairs a generator with a verifier that has its own camera tools and reports average gains of about 35% on BlenderGym, with the caveat that results are bounded by what the inspection views can reveal ([VIGA](https://arxiv.org/html/2601.11109v2)); BlenderGym itself found that more verification queries improve results and that Claude was the most human-aligned verifier of the models it tested ([BlenderGym](https://blendergym.github.io)). In practice this is a contact sheet. A Claude Code and OpenSCAD write-up shows the minimal loop: render a PNG from the CLI, read it, check it against stated numbers, re-render from other angles, with the rules kept in CLAUDE.md ([Classmethod](https://dev.classmethod.jp/en/articles/summer-project-2026-claude-code-openscad-3dprint/)). Willison's agent built a model browser and image contact sheets for the same purpose. For web 3D the browser screenshot loop is widely reported to make visuals converge, but no source documents multi-angle or frame-sequence review of 3D animation by an agent; a debug URL that fixes seed, camera preset and animation time, captured headlessly into a filmstrip, is a design inference from these sources and from blendpipe's per-clip filmstrips, not a documented practice. Headless Chrome proves composition, colour, silhouette and pose, never phone performance.

Art direction is the other half, and the documented Claude projects mostly skip it. The advice available is from vendor blogs, but it is consistent with the benchmark failures: write an explicit style bible before generating batches (camera, palette, light direction, scale, shape and material rules), generate from approved reference images because prompts "are a weak long-term memory", and keep accepted and rejected examples ([spritecook.ai](https://www.spritecook.ai/blog/consistent-game-art-with-ai); [seeles.ai](https://www.seeles.ai/resources/blogs/ai-game-visual-consistency-across-assets)). Check each asset at its target display size ([seeles.ai](https://www.seeles.ai/resources/blogs/how-to-avoid-ai-slop-in-game-art)). Gate before building, as in Willison's prompt: "First research and then critique this design. Only build after we have agreed on any modifications." Every source that addresses it keeps a human as the final judge of looks, and one states plainly that passing numeric checks does not guarantee a good render. Research on art direction for young children's apps specifically returned almost nothing; that question is unanswered here.

## For Puddle Island, adopt the review loop and the bake script, not a 3D runtime

The table gives a verdict on each approach against this project's constraints: one developer, phones first, an offline PWA, an approved illustrated 2D look, and a rule that source art and preparation steps live in the repository. The verdicts are judgements drawn from the evidence above; no source tested this combination.

| Approach | Verdict | Deciding reason |
| --- | --- | --- |
| Current illustrated sprites on code-driven mesh rigs | Keep as the default | Already the assistant-authorable form of character animation; one image deforms, so no per-frame atlas cost; nothing found matches it for soft illustrated creatures |
| Contact-sheet and filmstrip review harness, with a render-only reviewer and a written style bible | Adopt now | The best-supported finding in the research; applies to the existing 2D rigs with no 3D at all, and fits the repo's scripted browser suites |
| Offline bake to sprites (headless Blender or Three.js in headless Chrome, run by a repo script) | Adopt selectively, as a pilot | Zero runtime cost and fully reproducible; pays off for turnarounds, many poses, wearables and props; the look needs approval first |
| Code-built 3D as a pose or turnaround reference for the image tool | Worth one cheap trial | Uses 3D for what models get right (overall shape) and leaves the shipped pixels to the illustrated pipeline; undocumented in any source |
| Hosted image-to-3D (Meshy 7.1, Tripo P1) with pinned model IDs | One paid month only if a bake pilot needs organic shapes | Non-deterministic and fast-changing; generated files and manifests must be committed as source art |
| Live Blender MCP sessions | Skip for production | Unsandboxed Python, state drift and nothing reproducible unless written back out as a script |
| AI auto-rigging and motion libraries | Skip | One walk per creature type, a different skeleton per mesh, humanoid-only text-to-motion |
| Three.js sharing Pixi's WebGL context at runtime | Not now | A large precached dependency, a restructured renderer start-up and iOS memory risk, for no current game need |
| `@pixi/3d` | Watch; revisit after a few releases | v0.1.0, licence not stated, needs pixi.js 8.23 while the repo is on 8.22, no model training data |
| Local generation on the Mac | Skip | Untextured output, 18 GB peak memory, and the one stylized test input failed |
| Spine, Rive or Lottie | Skip unless a human animator joins | Editor-centred formats with no evidence of good assistant authoring |

The pre-render route has a strong precedent and a known trap. Dead Cells used a 3D model and skeleton rendered to 2D sprites so that a single artist could afford retakes and add parts such as armour easily ([80.lv](https://80.lv/articles/case-study-dead-cells-character-art-pipeline)), while a developer who did the same in Blender warned that it is "very hard to avoid that '3D rendered' look" ([C-Dogs SDL](https://cxong.github.io/2017/03/3d-rendered-pixel-sprites)). Those are the stakes for this game: baked 3D buys guaranteed consistency across angles and outfits, and costs atlas memory and download size per frame, where a mesh rig deforms one image. Faces are a weak point in every source and are better kept as simple 2D shapes on top. A pilot should therefore start with a prop or one simple round creature, fix the toon shading, outline and light rig in a shared module, pin the Blender or Three.js version, record a manifest, and put the baked result beside the existing illustrated version at phone size for the developer to judge before anything else is built on it. No documented case exists of Claude automating a toon-shaded sprite-sheet pipeline end to end, so this would be first-hand testing, not a proven recipe.

## Conclusion

The research reverses the obvious expectation. The headline tools of 2026 (an official Blender connector, one-call mesh generators, auto-riggers) are the least useful for a small, style-consistent, reproducible creature game, while the unglamorous practices around them transfer directly: fixed-view contact sheets, a verifier that did not write the thing it is judging, numbers in a style bible to check against, and scripts as the only source of truth. Those practices would improve the 2D pipeline the project already has, which is the cheapest test of whether they are worth having before any 3D is attempted.

What would change the picture is specific and can be watched for: `@pixi/3d` reaching a stable release with a stated licence and reports from real iPhones; an independent evaluation of current Claude models on soft organic characters; and creature animation libraries or a shared-skeleton rigger that makes clips transferable across a cast. Until one of those arrives, 3D earns a place here as an offline tool that produces 2D pixels, and the open question is one only a side-by-side at phone size can answer: whether a baked creature can sit next to an illustrated one without looking like it came from a different game.
